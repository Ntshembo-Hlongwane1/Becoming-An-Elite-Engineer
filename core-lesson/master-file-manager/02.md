# RAII and Deterministic File Managment

Resource Acquisition Is Initialization (RAII) is the single most important design principle file handling in C++. It establishes direct and unbreakable relationship between lifetime of a resource and the lifetime of an object.

> RAII eliminates entire classes of erros that were common in earlier programming models

In the context of file I/O RAII means:

- One clear owner such that the opening and closing of the file are bound to the construction and destruction of that owner.

> THIS RULE IS NOT OPTIONAL IN PROFESSIONAL SYSTEMS.

- Violating it inevitably leaks to leaks, undefined behaviour, and subtle bugs that surface only under failure conditions.

## The cost of manual lifetime management

Before RAII became widely accepted discipline, file lifetime was managed manually. This apporach relies entirely on prammer discipline and is fragile by design.

```c
#include <cstdio>

void write_log(){
    FILE* file = fopen("log.txt", "w");

    if (!file){
        return;
    };

    fprintf(file, "Application started");

    if (EARLY EXIT CONDITION){
        return; // file leak
    };

    fclose(file);
}
```

> Every new control path introduces the risk of forgetting to release the resource as the function grows, correctness becomes harder to reason about

## RAII-Based File Ownership

```cpp
#include <fstream>

void write_log(){
    std::ofstream file("log.txt");
    file << "Application started";
}; // FIle close automatically here
```

This simple pattern provides strong guarantees:

- Files handles are never leaked
- Cleanup happens predictably at scope exit
- Exceptions cannot bypass cleanup logic

## Exception Safety Through RAII

One of the most critical adavnatges of RAII is exception safety. WHen an exception is trhown, stack unwinding ensures that all local objects are destroyed in reverse order construction.

```cpp
#include <fstream>

void write_log(){
    std::ofstream file("log.txt");
    file << "Application started";

    throw std::runtime_error("unexpected failure")
}; // FIle close automatically here despite the exception
```
> Without RAII, this behaviour would require complex and error-prone cleanup logic

## Single Ownership and Scope Discipline

A fundamental rule of RAII-based design is that a resource must not outlive its owning scope. *Passing around raw file handlers or references to streams whose lifetime is unclear breaks the rule.*

```cpp
std::ofstream* global_file; // dangerous

void init(){
    global_file = new std::ofstream("log.txt");
};
```
> THis design hides ownership, complicate shutdown, and introduces leaks.


Correct design keeps ownership explict:

```cpp
void write_log(std:ofstream& file){
    file << "message\n";
};
```

> Here, the function uses file without owning it. Ownership remains clear and centrailized.

## RAII and OBject Composition

RAII scales naturally through compositions. Class that contain file streams auto manage their resources.

```cpp
#include <fstream>
#include <string>

class Logger {
    std::ofstream file_;

    public:
        explicit Logger(const std::string& path) : file_(path) {}

        void log(const std::string& msg){
            file <<  msg << '\n';
        };
}
```
> When a Logger object is destroyed, the file is closed automatically. No explicit clean code required.

## RAII as Design Contract

RAII is more than a convenience; it is a design contract. When a class owns a file, that ownership must be:
- Visible in the constructor
- Exclusive or clearly shared
- Bound to object lifetime

Violating this contract undermines determinism and predictablity

## Why Determinisitic FIle Management Matters

File I/O interacts directly with the OS and hardware. Leaked file descriptors can exhaust system limits. Delayed cleanup can lock file unexpectedly. Non-deterministic behavior makes failure hard to reproduce.

RAII enusre that file management remains deterministic, even in the prescence of errors, early returns or exception. This predictablity is not optimization. Its a prerequisite for building reliable systems.
