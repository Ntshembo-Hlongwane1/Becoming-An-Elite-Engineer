# Introduction to OOP in C++

## Definition of Object-Orientated Programming

In C++ OOP is a methodology for structuring software around types that model responsibility. The primary goal for OOP in C++ are:

- Encapsulation of state and invariants
- Clear and min public interfaces
- Explicit ownernership and lifetime managment
- Controlled use of polymorphism


### Core Concepts of Object Oriented Programming

- **Encapsulation:** This is separating of interface from the implementation and preventing uncontrolled access to **object state**

- **Abstraction:**  This in C++ means exposing only what clients must know while hiding implementation details.

- **Inheritance:** Inheritance is reserved exclusively for modeling true substituability. **Core Guidelines strongly discourage using inheritance for code reuse**

- **Polymorphism:** This allows for different implementations to be accessed through common interface 

### Classes and Objects in C++

A class defines a type, including it's invariants, operations, and representation. Then an object is a concrete instance of that type with a well-defined lifetime.

**Example**

```cpp
#include <iostream>
#include <string>

    public:
        Car(std::string brand, std::string model, int year) : brand_(std::move(brand)), model_(std::move(model)), year_(std::move(year)) {}
```

## Differences Between Classical and Modern C++ in Object-Oriented Programming

C++11 and beyond introduced fundamental change that improves safety, expressiveness, and correctness of OOP design

### Overview of Key Difference

- Constructors and memory managment
- Inheritance and polumorphism
- Smart pointer and ownership
- Move semantics
- Type deduction with **auto**
- Lambda expressions
- Modern template facilities
- Compile-time programming with **constexpr**
- Concurrency and object safety

#### Constructors and Memory Management

In classical C++, constructors and destructors were responsible for manual resource management. Dynamic allocation relied on the **new** and **delete** making it programmers responsibility

**Example**

```cpp
class Resource {
    public:
        Resource(){
            std::cout << "Resource acquired\n";
        };

        ~Resource(){
            std::cout << "Resource released\n";
        }
}

int main(){
    Resource r = new Resource();
    delete r; // omission lead to a leak
}
```
> This pattern was fragile and prone to leaks and undefined behavior

**Modern C++** enforces **RAII** through standard lib types that express ownership explicitly. Memory management is deterministic and exception-safe by design

```cpp
#include <memory>

int main(){
    auto r = std::make_unique<Resource>();
}
```
> The resource is released automatically when the owning object goes out of scope

### Inheritance and Polymorphism

**Classical C++** inheritance and polymorphism existed but lacked safe guards and relied on programmers discpline. Common issues included missing virtual destrutors, accidental overriding, and unsafe raw pointers

```cpp
class Animal {
    public:
        virtual void sound(){
            std::cout << "Animal sound\n";
        };
}

int main(){
    Animal a = new Animal();
    delete a;
}
```
> This design risk undefined behaviour when used polymorphically

**Modern C++** strengths polymorphic design using **override**, **final**, and mandatory virtual destrutors

```cpp
class Animal{
    public:
        virtual Animal() = default;
        virtual void sound() const = 0;
}

class Dog final : public Animal {
    public:
        void sound() const override {
            std::cout << "Barking\n";
        };
}
```
> This design is explict, safe and self-

### Smart Pointer and Onwership Semantics

**Classical C++** ownership was implicit and undocumented. Misue of raw pointers

**Modern C++** ownership is expressed explicitly using smart pointer:

- **std::unique_ptr** for exclusive ownership
- **std::shared_ptr** for shared ownership
- **std::weak_ptr** to break cycles

### Move Semantics

**Classical C++** Copying was the primary mechanism for tranferring resources, often resulting in unnecessary overhead

**Modern C++** move semantics allow for efficient tranfer of resource without duplication 

```cpp
class Data {
    Data() = default;
    Data(const Data&) {
        std::cout << "Copy\n";
    };
    Data(const Data&&) noexcept {
        std::cout << "Move\n";
    }
}

Data a;
Data b = std::move(a);
```

### Type Deduction with auto

**Classical C++** required explicit type declaration leading to verbosity and reduced maintainbility

**Modern C++** auto enables precise type deduction while preserving static typing 

```cpp
auto count = std::vector<int>{1, 2, 3}.size();
```

### Lambda Expression 

**Classical C++** callbacks required function pointers or functor classes

**Modern C++** lambda expression enables localized behaviour with clear intent

```cpp
std::for_each(values.begin(), values.end(), [](int v) {
    std::cout << v << ' ';
})
```
